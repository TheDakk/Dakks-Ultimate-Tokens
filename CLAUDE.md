# Claude Code: how this library is produced and reviewed

Invoke the `foundry-art-pipeline` skill first; it carries the general method. This file is
the project-specific state and the exact moves. Codex's side of the same contract is
`AGENTS.md`. The human procedure is `upload/README-UPLOAD.md`.

## The route in one paragraph

Images come from Codex's built-in image tool (no OpenAI API; Nick chose the Pro plan). Each
row's prompt (template `dakk-production-v4`) asks for the subject on a flat magenta fill.
`import_builtin_image.py` keeps the untouched capture under `masters/_captures/`, keys it
with `chroma_key.py` into the RGBA master, exports the WebP (plus a copy in every other
directory the row's notes say it serves; `sync-copies` repairs missing ones), and appends
`results-*.jsonl`. Revisions of approved rows go through `--polish` (preamble in
`POLISH-PREAMBLE.txt`, image-to-image from the capture) or `--revise <reason>` (a fresh
generation on a corrected brief); the importer retires the old files to `_superseded/` as
`<stem>-<date>-<reason>-v<N>` and bumps `art/versions.json`, which the generator copies into
the workbook's version column. Filenames never carry a version. `changelog.py` classifies
every revision (redesign / change / polish, by measured difference) into `CHANGELOG-2.0.md`;
`prune_superseded.py` deletes only minor-polish predecessors whose hash is in a verified
backup manifest. The 2.0 plan of record is `PLAN-UNIVERSAL-2.0.md`.
`verify_gate.py` is the automated gate Codex runs after each block. `npm run art-check` (in
`C:\Projects\FoundryVTT\DnD2E`) is the suite's intake gate. The handshake that proves a
reader is on the real queue: `Black Dragon · black-dragon.webp · 1200 · 4e161de44abf`
(changes whenever JOB-0001's prompt changes; keep README-UPLOAD and generate_tokens.py in step
with it).

## Invariants (violating any of these is how a day gets lost)

- One interpreter: the queue is generated by `DnD2E/tools/gen-art-worklist.mjs` and read
  verbatim. Never edit the CSV, never let anyone reword a prompt at send time. A brief is
  changed in the generator, the queue is regenerated, and the changed-hash count is checked
  to be exactly the rows intended.
- The workbook has ONE writer: `npm run art-upload`. Never round-trip it through openpyxl;
  never copy `dist/*.xlsx` over it. Validate after every write (structure, table names,
  merges; `exceljs` and Excel both open it).
- Captures are never touched. Every keyer improvement is applied by re-keying from captures
  with `rekey_rows.py <suffix> --all-captured`; prior files go to `_superseded/`.
- HISTORY (workbook sheet) is append-only; log every generator, keyer or procedure change
  with `append_history.py` (in-place ZIP rewrite; the old scratch `append-hist` is gone) or an equivalent that finds the last
  `HIST-` row and grows `HistoryTable`.

## Fixing a brief (the standard move)

1. Add the row's slug to `SUITE_LOOK` (creatures) or `ITEM_LOOK` (gear) in
   `gen-art-worklist.mjs`; or fix the deriving rule if a class is wrong (see
   `anatomyBrief` head-count rule).
2. `npm run art-worklist` twice (byte-identical), diff prompt hashes against the pre-change
   CSV: the changed set must be exactly the intended rows; JOB-0001 unchanged.
3. `npm test` (134+), `npm run art-upload`, validate the workbook, append a HISTORY line.
4. Retire the row's master, export and capture to `_superseded/<dir>/<name>-<date>-<why>`.
5. Give Codex the row list with the final queue sha256 and "fresh prompt-json".

## Reviewing a block (all of it, never a sample)

`review_sheets.py` lays every master out in labelled contact sheets in job order; look at
every sheet. Judge: right subject, right head/limb count, one isolated figure, TSR oil look,
no bleed. Then the numbers: `verify_gate.py --all` (corners, hot magenta, green rim, rose by
hue). Retire what fails; fix the class it belongs to, not just the row. Known truth: my image
viewer misled me twice on pink; pixel measurements of the file are the arbiter.
A failure that is the subject's own colour (a jade idol reads as a green rim) is accepted by
file hash in `verify-accept.json`, with the reason; a regenerated file is checked again.

## Keyer rules (chroma_key.py, v3.9)

Alpha = the more opaque of colour-distance and magenta-ness ramps; partial alpha only near
pure key or strongly magenta pixels; pure-key pixels forced to 0; NO algebraic un-mixing
(overshoots into green whenever alpha is underestimated, which it is on pale edges); rim
spill removed within 3px and on every partial pixel; interior bleed margin 30 dark / 12
bright; rose (hue 315-360, low saturation) pulled fully on partial, halfway on opaque. Measure
rose by hue, not min(R,B)-G.

## Refusals

Output-stage refusals are stochastic: one retry. Input-stage refusals are deterministic:
change the brief. A row refused twice on a corrected brief is dropped and noted.

## Collections (settings never mix)

`universal` is the generic D&D / Forgotten Realms look and is complete (1408/1408),
closed, and rebuilt; no further Universal generation is authorized. `darksun` is next and
is a separate collection, but it remains blocked until all four prerequisites exist: an
accepted `darksun-sheet` reference and its hash; its own contract; its own queue and queue
hash; and its own handshake. A campaign consumes universal assets but never overwrites one;
a setting-specific version of a shared subject is a new row and slug. Never run two
collections in one Codex session; the attached reference holds the style. When a future
suite names a subject differently, the answer is `art/aliases.json` (alias slug -> canonical
slug, no chains) consulted by that suite's `resolveArt`, never a duplicate file. See
README.md "Collections and settings".
